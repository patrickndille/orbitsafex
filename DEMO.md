## 1. Winning Demo Strategy

**Emotional hook:** Tens of thousands of objects share Low-Earth Orbit at up to 15 km/s. At that speed a small debris fragment is catastrophic. Most small satellite teams have no tool to turn raw orbital data into a decision they can act on. OrbitSafe AI is that tool.

**Technical proof:** The demo shows a complete pipeline — Space-Track GP telemetry, a stratified LEO sample propagated with SGP4, a spatiotemporal prefilter that finds future-converging pairs, TCA refined by bisection, and a screening Pc computed from a 2-D Gaussian integral. The core encounter metrics — TCA, miss distance, relative velocity, and screening Pc — are computed by the physics engine, not generated by the LLM.

**AI differentiator:** The language model receives those calculated screening metrics and produces a structured advisory with general candidate options for specialist review. It does not calculate the Pc. It explains it. That boundary is on screen in the interface at all times.

**Credibility signal:** Scientific limitations are disclosed in the interface itself — not in a README footnote. The Pc disclaimer appears in amber. The encounter inset is labelled "magnified — not to scale". The dashboard footer names the data source, the propagator, and the triage engine. Trustworthiness is a design decision.

**Final impact message:** OrbitSafe AI gives CubeSat teams, emerging space agencies, and research institutions a structured, evidence-grounded triage workflow — without needing a flight-dynamics department to interpret it.

## 9. What Makes This Entry Different

### 1. Physics before language generation

OrbitSafe AI's astrodynamics engine — SGP4 propagation, spatiotemporal KD-Tree prefilter, GMST-aware geodetic conversion, and 2-D Gaussian Pc integration — runs entirely in Python before the LLM is invoked. The LLM receives calculated screening metrics, not raw orbital elements. Miss distance and Pc are computed and displayed independently of the LLM; the prompt instructs the model to explain those supplied values without replacing them.

Generic AI chatbots asked about collision risk have no physics engine. They pattern-match against training data and may produce plausible-sounding numbers with no relation to the actual orbital geometry.

### 2. Transparent scientific limitations and advisory boundaries

The Pc disclaimer, the "not to scale" inset label, the advisory footer, and the dashboard footer ("Orbital data via Space-Track.org · SGP4 propagation · LangChain triage") are all present in the production interface. They are not in a README footnote — they are on screen during the demo. A trustworthy system that acknowledges its limits is more useful for decision-support than one that overstates its precision.

### 3. A complete path from orbital telemetry to visual, understandable triage

From authenticated Space-Track GP ingestion → stratified LEO sampling → spatiotemporal prefilter → SGP4 TCA → screening Pc → interactive Three.js globe → magnified encounter inset → structured AI triage drawer with LaTeX-typeset probabilities: every stage is implemented, tested, and visible in the running application. The result is a decision-support workflow that a non-astrodynamicist can follow and that a specialist can audit.

## 13. Claims Checklist

### Safe, verified claims

These claims are supported by the implementation code, database inspection, and current documentation:

- OrbitSafe AI ingests GP/OMM orbital data from Space-Track.org with session-cookie authentication and a local disk fallback.
- Orbit propagation uses the SGP4 model via the `sgp4` Python library (Vallado implementation).
- The spatiotemporal prefilter propagates a stratified sample of LEO objects at 5-minute coarse intervals over a 24-hour window and uses a KD-Tree at each epoch to find pairs passing within the screening radius at any future time — not just at the current epoch.
- TCA is refined by bisection (20 iterations) for sub-second accuracy.
- The screening Pc uses an assumed isotropic σ = 200 m and integrates a 2-D Gaussian over the combined hard-body cross-section via `scipy.integrate.dblquad`.
- Risk tiers: CRITICAL (Pc ≥ 1×10⁻⁴), HIGH (1×10⁻⁵ ≤ Pc < 1×10⁻⁴), ELEVATED (1×10⁻⁶ ≤ Pc < 1×10⁻⁵), MONITOR (Pc < 1×10⁻⁶).
- The database contains 64 saved scans.
- Scan 54 contains an event classified as CRITICAL tier: FENGYUN 1C DEB (#29944) vs OBJECT D (#100328), miss distance 0.21 km, relative velocity 5.98 km/s, screening Pc ≈ 1.80×10⁻⁴, TCA 2026-08-22T04:31:30Z, `position_source = "tca"`.
- Globe markers are geographic midpoints computed from primary and secondary positions at each event's own TCA — not a simultaneous orbital snapshot.
- GMST rotation is applied to convert TEME/ECI to Earth-fixed coordinates.
- The encounter inset is magnified and explicitly labelled "Encounter geometry magnified — not to scale".
- The auto-spin is cosmetic and does not represent orbital motion.
- The AI triage response is Markdown + LaTeX rendered via `react-markdown`, `remark-math`, and `rehype-katex`.
- Every AI triage response includes a mandatory advisory disclaimer (hardcoded in `TriageDrawer.tsx` and enforced in the LLM system prompt).
- The LLM system prompt instructs the model to use advisory language, not guarantee collision, and not invent or calculate Pc.
- The triage request payload sent to the LLM is: primary satellite name, NORAD ID, miss distance, relative velocity, and screening Pc. Secondary object identity, TCA, and orbital geometry are displayed in the drawer's metrics grid but are not part of the LLM request.
- The backend has 21 pytest tests; the frontend has 64 Jest tests; total: **85 automated tests**.
- IBM Bob was the primary development tool used for every component.

The `position_source = "tca"` flag only means TCA coordinates were computed by SGP4 — it does not prove whether the GP input came from a live Space-Track fetch or from `gp_fallback.json`, and it does not prove the event was not inserted for validation or testing purposes. ### Click sequence clarification

Clicking a row in `ConjunctionTable.tsx` calls `onSelectEvent`, which in `page.tsx` sets `selectedEvent` — and `TriageDrawer` auto-fetches on `event?.norad_id` change. **There is no separate "lock without opening triage" interaction.** The correct sequence is: hover → describe the globe and inset → click once → drawer opens automatically. The §5 shot list and §7 click path reflect this correctly.

### AI triage payload clarification

The `requestTriage` call sends: `sat_name`, `norad_id`, `miss_distance_km`, `relative_velocity_kms`, `pc_value`. It does not send: secondary object identity, TCA timestamp, orbital geometry, covariance, mass, or spacecraft capabilities. The secondary name and TCA visible in the drawer's metrics grid come from the `ConjunctionEvent` object in frontend state — they are displayed by the React component, not returned by or sent to the LLM. Delta-V estimates in the AI response are general candidate values, not computed for the specific spacecraft.

### README versus code discrepancies

1. **"Real-time"** in the README subtitle: scan takes 30–90 s depending on server load and object count. Aspirational. Omit or qualify.
2. **"Alfano Pc"** in README solution table: isotropic σ = 200 m, not full encounter-plane covariance projection. Always say "screening Pc".
3. **"up to 15 km/s"**: physically correct as a maximum for retrograde LEO encounters. The demo event is 5.98 km/s — well within the range.
4. **OBJECT E vs OBJECT F** (NORAD #100360 vs #100361): present in the database with the second-highest Pc values but with anomalously low relative velocity (~0.002 km/s), suggesting co-orbital elements. Do not use this event — the velocity invites questions that are hard to answer in 30 seconds.
5. **Test count**: 21 backend pytest + 64 frontend Jest = **85 total** (not 41 as previously stated). Verify by running both suites immediately before recording.
