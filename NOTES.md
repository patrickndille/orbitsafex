# Space debris tracking and collision avoidance AI (OrbitSafe AI)

Real-time space debris conjunction warning and AI-assisted triage dashboard.
AI recommendations are advisory only and require flight-dynamics team review before any maneuver is authorised.

## CONCEPT

Space debris tracking and collision avoidance (OrbitSafe AI) is a real-time space debris conjunction warning and AI triage dashboard.

Low-Earth Orbit (LEO) is increasingly congested, making debris tracking and collision prevention a critical challenge. True collision risk requires projecting orbits forward in time and calculating statistical probabilities based on relative velocity, positional covariance, and encounter plane geometries, rather than relying on raw arbitrary distance thresholds.

## Initial Scope

1. **Data Ingestion & Caching**
Fetch TLE (Two-Line Element) data from the CelesTrak API (Open source). Implement caching and rate-limiting to manage large catalog sizes without overloading the endpoint.

2. **AI Anomaly & Risk Scoring ($P_c$ Math)**
Use Python (`sgp4`, `numpy`, `scipy`) to propagate TLEs forward in time.
Calculate a Screening Probability of Collision ($P_c$) using a fixed isotropic 2-D Gaussian model.
Use an LLM to ingest these metrics and surface high-priority alerts.

3. **Natural Language Operator Query**
Allow mission operators to ask questions like:
* "Which satellites have a screening $P_c > 1\%$ in the next 24 hours?"
* "What candidate maneuver directions should be reviewed by the flight-dynamics team?"

4. **Interactive Dashboard**
Build a simple React/Next.js interface displaying high-risk conjunction events on a 3D Earth globe (using Three.js) with plain-language risk summaries generated by AI.

5. **Project Documentation**
A full `README.md` detailing the problem, solution, AI architecture, and how IBM Bob was utilized.

## Architectural Transition: From CelesTrak to Space-Track.org

During development, data ingestion was migrated from **CelesTrak** to **Space-Track.org**.

* **Primary Rationale for Migration:**
  * **Data Timeliness & Accuracy:** Space-Track.org is operated directly by 18th Space Defense Squadron (18 SDS), serving as the authoritative source for General Perturbations (GP) element sets and satellite catalog data.
  * **Rate Limiting & Reliability:** Direct authentication against Space-Track via session cookies (`/app/data/whoami`) provides robust query access without encountering non-deterministic web-scraping rate limits or public mirror delays.
  * **Granular Query Filtering:** Space-Track enables server-side filtering via REST API endpoints, substantially reducing initial bandwidth and client-side processing loads.

* **Fallback Strategy:** Successful responses automatically maintain a local JSON fallback (`data/gp_fallback.json`) to guarantee zero-downtime offline operational resilience.

## Core Logic (The Physics)

Instead of a flat distance threshold, the system evaluates real conjunction risk:

* **SGP4 Propagation:** Propagate TLE/GP element sets forward to find the Time of Closest Approach (TCA).
* **Spatiotemporal Prefilter ($O(n\log n)$ Optimisation):** Propagate all satellites at coarse intervals across the 24-hour window and build a KD-Tree at each epoch. The union of pairs that enter the screening radius at **any** epoch is forwarded to the expensive fine TCA search. This finds pairs that are far apart at t=0 but converge later — the prior current-epoch-only snapshot would miss them. Known limitation: fast-pass conjunctions (relative speed > `COARSE_SCREEN_KM / COARSE_INTERVAL_S`) can still escape detection between coarse epochs.
* **Stratified Altitude Sampling:** Objects are sampled proportionally across 50 km altitude bins rather than truncating by altitude sort, ensuring full 300–1200 km band coverage without low-altitude bias.
* **Epoch-Aware TEME→Geodetic Conversion:** SGP4 outputs TEME/ECI coordinates. Geographic longitude is computed by applying the Greenwich Mean Sidereal Time (GMST) rotation at TCA epoch before converting to lat/lon. Raw inertial longitude is NOT used as geographic longitude.
* **Screening Probability of Collision ($P_c$):**

$$P_c = \frac{1}{2\pi \sigma^2} \iint_{A} \exp\left(-\frac{|\vec{r} - \vec{r}_0|^2}{2\sigma^2}\right) dx\, dy$$

where $A$ is a disk of radius $r_{hbr}$ (hard-body radius), $\vec{r}_0$ is the miss vector, and $\sigma = 200\ \text{m}$ is an assumed isotropic uncertainty. No object-specific covariance matrix is used. This is a screening estimate, not an authoritative CDM-quality Pc.

**Remaining known limitations:**

* $P_c$ uses a fixed isotropic σ=200 m; no object-specific covariance matrix. An authoritative operational Pc requires CDM data.
* The triage endpoint returns a single JSON response; it does not stream.
* Fast-pass conjunctions (high relative velocity) can escape the coarse prefilter between samples.
* GMST approximation is first-order; accuracy ≈ 0.1° in longitude.
